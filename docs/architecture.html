NautilusTrader Market-Data Dashboard

How commands and information move through the system — market data, subscriptions, portfolio snapshots, order events, equity, and the live/test split. Every arrow below maps to a real function or Redis key in the codebase.

One sentence: a single NautilusTrader live node ingests Binance market data and runs the strategies + a simulated (sandbox) exchange; a ControlActor and the strategies publish everything the UI needs into Redis; a FastAPI server tails those Redis streams/keys and pushes them to the browser over a WebSocket; the browser draws it on a canvas. Commands flow the other way through Redis command streams.

Components

Python process Redis Browser External

TradingNode scripts/binance_data.py

The Nautilus live node. Hosts the Binance data clients (real LIVE public feed), the sandbox execution client (simulated fills), the ControlActor, and the two strategies. Its MessageBus and Cache are backed by Redis DB0 with stream_per_topic=True, so every bus message is mirrored into a Redis stream.

ControlActor src/trading/actors/control_actor.py

The bridge to the UI. Polls the command stream to (un)subscribe instruments for the chart, and on a 1s timer publishes the portfolio snapshot, equity points, and computed indicators into Redis.

Dashboard server server/app.py

FastAPI. Tails Redis streams and pushes frames over a per-mode WebSocket; serves REST for equity/positions; relays UI commands into Redis command streams. Holds no trading state of its own.

Browser client server/dashboard.html

Dependency-free canvas UI. One WebSocket carries ticks, bars, portfolio, order events, and indicators; REST is used for equity and a positions fallback.

Redis topology — two databases

Market data is shared; trading state is split by UI mode.

DB0 — live LIVE_REDIS_URL

The live node's cache + message bus, all market-data streams (stream:data.trades.*, stream:data.bars.*), and every dashboard:* key the ControlActor/strategies write. Both UI modes read market data from here.

DB1 — test TEST_REDIS_URL

Backtest results only: dashboard:backtest:* and test:chart:*. The dashboard reads test-mode state (positions/equity/bars) from here, while still reading live market data from DB0.

Command streams always target DB0. In app.py, _send_command() and _send_strategy_command() write to the live connection r regardless of the client's mode — that's where the node listens.

Live vs Test mode

The ?mode= WebSocket query param (and REST path prefix) selects which backend a client talks to. Strategies are tagged live or test in dashboard:strategy_modes; the server filters positions/PnL/order-events by that tag so the two tabs never bleed into each other.

Flow 1 — Market data → chart

Binance trades/klines/depth become ticks and candles on screen.

  1. Binance → data client. node The Binance adapter streams aggTrades, klines, and (for the SAR strategy) L2 depth into the internal MessageBus.
  2. Bus → Redis. node With stream_per_topic=True, each message is mirrored to a Redis stream, e.g. stream:data.trades.BINANCE_FUTURES.BTCUSDT-PERP and stream:data.bars.…-1-MINUTE-LAST-EXTERNAL. (Order-book deltas are excluded via the bus types_filter so they never hit Redis.)
  3. Server tails. app.py _tail_symbol() resolves the trade key with find_trade_key() and XREADs it; _tail_bars() does the same per bar-type. Each keeps retrying to find its key as long as a client is subscribed (thin instruments create their stream only on first trade).
  4. Server → browser. app.py New entries are pushed as {type:"ticks"} / {type:"bars"} frames to every socket in symbol_clients / bar_clients.
  5. Browser renders. client onTicks() / onBars() append to the active panel and render() → drawLine()/drawCandles() on the canvas. The tick line, candles, trade tape, and watchlist last-price all derive from these two streams.
History on open comes from _send_history() (ticks) and _send_bar_history() (bars, merging the historical.* and live streams) before the live tail starts.

Flow 2 — Subscriptions

What happens when you add an instrument to the watchlist (or click a position).

  1. Client asks. client addSymbol() → ws.send({action:"subscribe", symbols:[id], window}).
  2. Server fans out. app.py Adds the socket to symbol_clients/ind_clients and, for every timeframe, to bar_clients[bar_type]. Sends history, starts tails (_ensure_tail, _ensure_bar_tail, _ensure_indicator_tail).
  3. Server → node command. app.py _send_command({action:"subscribe", instrument_id, bar_type}) → XADD dashboard:commands (DB0), one command per bar-type + trades.
  4. ControlActor subscribes. node _poll_commands() reads the stream; _on_command() calls subscribe_trade_ticks() / subscribe_bars(). Subscriptions are deduped (a re-sent subscribe is a no-op) so reconnects don't spam the aggregators.
  5. Data flows. node→redis→app→client The data client now streams that instrument → Redis → the tails from Flow 1 deliver it. Unsubscribe (× button) sends {action:"unsubscribe"}; the server drops the socket from the client sets (_drop_bars_for_symbol).

Flow 3 — Portfolio & positions

Open/closed positions, per-strategy PnL, and the trade markers on the chart.

  1. Snapshot built. node ControlActor._snapshot_portfolio() runs every 1s: iterates cache.positions_open()/positions_closed(), reads portfolio.unrealized_pnl() and net_exposure(), and copies newly-closed positions into a persistent map (the exec cache purges closed positions, so the dashboard keeps its own history).
  2. Written to Redis. node The whole snapshot (positions, closed_positions, prices, pnl, overall_pnl) is SET to dashboard:portfolio (DB0); closed positions are also persisted to dashboard:closed_positions so markers survive restarts.
  3. Server reads & filters. app.py _portfolio_loop() (every 0.25s) calls _build_portfolio_sync(mode): reads dashboard:portfolio, looks up dashboard:strategy_modes, and keeps only this mode's strategies (live = tagged-live + untagged; test = tagged-test), recomputing PnL from the filtered set. Test mode also merges DB1 backtest positions.
  4. Server → browser. app.py A signature check suppresses duplicate frames; changed snapshots go out as {type:"portfolio"} to that mode's sockets.
  5. Browser renders. client onPortfolio() stores lastPortfolio; renderPositions() draws the tables and metric tiles, and _tradeMarkers() derives the entry ▲ / exit ▽ flags for the active instrument from the same object.
The persistent closed-positions map is never trimmed and is re-serialized every second — a known scaling cost for very long sessions.

Flow 4 — Order events

  1. Strategy emits. node On submit/fill/reject/cancel, the strategy's _publish_order_event() does XADD dashboard:order_events (DB0), tagged with its strategy id.
  2. Server routes by mode. app.py A single _tail_order_events() reads the stream, looks up each event's strategy mode (_event_mode, untagged→live), and pushes only to that mode's sockets. On connect, recent events are replayed — filtered to the client's mode.
  3. Browser shows. client onOrderEvent() maintains a per-strategy rolling order log (pending → accepted/rejected). Cleared on mode switch so reconnect replays don't duplicate.

Flow 5 — Equity, return & drawdown

  1. Live points. node Every 5s, _snapshot_portfolio() appends a mark-to-market point (nav = 100000 + realized + unrealized) to dashboard:equity:live / dashboard:equity:test, and tracks the high-water peak.
  2. Backtest curve. backtest_runner Writes a per-bar mark-to-market curve to dashboard:backtest:equity and its ending NAV to …:end_nav.
  3. Server stitches. app.py _account_equity_sync(mode): live mode returns dashboard:equity:live; test mode concatenates the backtest curve with the live test points, offsetting the live portion by nav_offset = end_nav − 100000 for continuity.
  4. Browser derives all three. client renderAccount() plots NAV, computes return = nav/START−1, and a running-peak drawdown; the price chart's drawdown subplot uses the same high-water-mark logic on the instrument price.

Flow 6 — Indicators

Two producers write to dashboard:indicators:{instrument} (DB0): the ControlActor computes SMA/RSI/VWAP/Bollinger/Ichimoku per bar (_feed_and_publish_indicator), and the strategies publish their already-warmed fast/slow EMAs (_publish_indicator) so the chart draws the exact lines the strategy trades on — no cold-start recompute. The server's _tail_indicators() streams them; the client merges by timestamp and overlays them on the candles.

Flow 7 — Strategy control (arm / start / stop)

  1. UI action. client Start/stop/close/export buttons send a strategy action over the WebSocket.
  2. Server relays. app.py _send_strategy_command() → XADD dashboard:strategy_cmds (DB0), and tags the strategy's mode in dashboard:strategy_modes.
  3. Manager acts. node thread _strategy_manager() polls the stream: start_strategy → arm (_active=True) + reset() + start(); stop_strategy/close_strategy → disarm, cancel/close, stop; state is written to dashboard:strategy_states. Strategies auto-stop on node startup so nothing trades until you press Start.
  4. On start. node Strategy.on_start() (when armed) registers indicators, subscribes to its bars + L2 order book, and warms the EMAs from REST history.

Flow 8 — Backtest & live handoff

  1. Kick off. client→app start_test_strategy (optionally with a date range) → dashboard:strategy_cmds, tagged test.
  2. Runner thread. node thread run_backtest() fetches Binance 1m klines (throttled REST), feeds a BacktestEngine (HEDGING, 10× leverage, bar_execution), then writes results to DB1: dashboard:backtest:positions, a mark-to-market …:equity, per-instrument …:bars/…:indicators, and chart bars under test:chart:*. Open positions are force-closed at the last bar so nothing bleeds into live.
  3. Dashboard shows it. app→client Test-mode reads state from DB1 and merges backtest positions into the portfolio frame; the chart overlays test:chart:* bars.
  4. Optional live handoff. node thread If no end-date was given, after the backtest the manager arms + starts the live strategy, and the test equity continues from the backtest's ending NAV via nav_offset.

Execution model (sandbox)

Fills are simulated locally by a SandboxExecutionClient for BINANCE_FUTURES — there is no real order placement. Key settings (binance_config.py):

SettingValueWhy
book_typeL2_MBPMarket orders walk real depth → full-size fills with slippage (vs L1 top-of-book capping fills).
oms_typeHEDGINGEach entry is a separate position (matches the backtest venue).
default_leverage10×50 positions × $2000 = $100k notional → only $10k margin, so the cap doesn't exhaust the balance.
trade_executionFalseTrades arrive with offset timestamps → "stale trade" noise; the L2 book drives fills instead.

The L2 book is fed by the strategy subscribing to Binance partial-depth (subscribe_order_book_deltas). These deltas reach the matcher in-process only — the bus types_filter keeps them out of Redis to avoid flooding it. The backtest can't use L2 (klines carry no depth), so it fills at the bar close via bar_execution — the one place live and backtest genuinely differ.
